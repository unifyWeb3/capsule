# Capsule

**A spending record for AI agents. Chain-verified where the chain can prove it, honest about the rest.**

Your agent asked for $0.05 of market data. Your cap was $0.002 a call, $0.0025 in
total. The Passport refused it.
Nobody knew what your limit had just cost you, because nothing else records what an agent
was refused, at the real price, against the budget you signed with a passkey.

Capsule records it. Every purchase, every refusal, and the price of each.
SERV Reasoning decides what to buy. Your Kite Passport session holds the cap.
The record keeps both halves.

## How it works

1. **You set the cap.** A Kite Passport session, approved with your passkey: a limit per
   call, a total budget, and an asset. The cap lives in Kite's backend, not in the agent's code.
2. **The agent asks. The Passport decides.** SERV Reasoning proposes one purchase at a time.
   The Passport checks every amount against the session and refuses in its own code.
   The agent can try for the better answer. It cannot pay for it.
3. **Capsule records and proves.** Every attempt is written to a hash-chained log, signed by
   the agent's Kite-bound key. Every payment is re-read from the chain when the proof is made.

   20.4× the whole budget.**

## Price a limit before you sign it

A cap is a number you sign with a passkey, and until now the only way to learn what it
costs was to spend it. The recorded run spent it and kept the bill: **$0.051 of refused
evidence against a $0.0025 budget, 20.4× the whole budget.**

**/cost prices that trade for any set of facts and any pair of caps**, over the live Kite
service catalog, with the same solver:

```bash
curl "https://capsule-phi-blond.vercel.app/api/limit-cost?facts=current%20ETH%20price%20and%2024h%20change,search%20interest%20and%20trend%20over%20the%20last%20month&per_tx=0.002&total=0.0025"
```

Your facts are priced over the catalog as it stands today, read over plain HTTPS with no
key, no account and no payment. The recorded run is priced over the catalog of the day it
ran, because that is the catalog its prices belong to. The answer always says which
catalog it used and when it was read.

The solver is exact, not clever. It enumerates the subsets of your facts, costs the
cheapest endpoint that covers each one, takes the basket that fits inside your caps, and
reports what is left over. There is no model in the loop and no cut-off, so the same inputs
always give the same answer. Four rules keep it honest:

| Rule | What it means |
| --- | --- |
| **Demonstrated or declared** | A cover is either an endpoint the record already shows being chosen for that fact, with its price and transaction, or one whose own catalog text claims the fact. The answer says which. |
| **A claim has to be complete** | Every meaningful word of the fact has to appear in the endpoint's own text. Strictness costs recall and buys a cover that is never claimed without something behind it. |
| **Nobody sells it, nobody prices it** | A fact no merchant claims is named and left out of the total, rather than given a number that nothing backs. |
| **A shared endpoint is counted once** | If one endpoint would have covered two facts, it is priced once, because that is what it would have cost. |

The run's own facts are the regression test: the solver, given the catalog of that day and the
record, arrives at **$0.051 and 20.4×**, the number the log measured. Two routes to the same
number, one from the chain and one from the catalog, and a test that fails if they ever
diverge. The live catalog in reach does not move it: a run's prices belong to its day.

The same answer is available as the `price_my_limit` tool in the `@oxunify/capsule-mcp` package, so
an agent can price its own limits before it asks for a session.

## The four anchors

The record is checkable without trusting this program.
| Anchor | Who decides it | How a judge checks it |
| --- | --- | --- |
| **The refusals** | The Kite Passport backend, not this code | `session_rule_exceeded` and `session_total_exceeded` are Kite's own error codes |
| **The payments** | The chain | USDC transfers on Base, re-read from the chain at request time by `/proof.json` |
| **The record itself** | The agent's identity | The log head is signed with the secp256k1 key the Passport binds to the agent's DID; the key is published by Kite |
| **The payer** | The session's wallet | Every transfer in the record is checked on chain to have come from the wallet that funded the session |

A fifth source sits beside the first, and it is not ours: the payment network's own ledger.
`/evidence.json` checks the record against it, and finds every payment the session made,
with its transaction, and none for the two refusals.

`npm run verify` runs the whole check against the live deployment and exits zero only if
all of them hold.

## What the network's ledger says

The log is the owner's account of what its agent did. Kite Passport keeps its own account:
every x402 payment with its transaction, and every spending session the owner approved with
a passkey. A refusal leaves no payment behind, so that ledger corroborates a refusal by the
absence of the thing a payment would have left, in a record this project did not write.

`/evidence.json` matches the two accounts mechanically, by session, address and amount.
For the recorded run they agree on all **7** attempts: **2** refusals left no payment,
**0** disagreements, and the session's totals agree at **$0.002**. The session was approved
by a passkey. The control holds: the same **$0.05** endpoint was paid, with a transaction,
under the larger cap.

The capture keeps the account's own identifiers out, and the file says which ones it kept
out. A judge can read the ledger the same way, with `kpass activity --output json`, or check
the payments on Base.

## Bring your own record

Capsule verifies any agent's spending record, not just Capsule's.

Publish your agent's decision log (a hash-chained JSONL file) anywhere that serves it over
https. Hand the link to whoever needs to see it. Capsule fetches the log, reads every
payment off the chain, and answers. The owner keeps their data. Nothing is stored here.

```bash
curl "https://capsule-phi-blond.vercel.app/verify?log=https://example.com/decision-log.jsonl&format=json"
```

Three independent checks:

| Check | Applies to | What it proves |
| --- | --- | --- |
| **The payments** | any log with a transaction hash | a transfer of the expected amount was paid on chain |
| **The refusals** | any log with a priced refusal | what the agent was refused and what it would have cost; the owner's account, corroborated by the payment network's ledger where we hold it |
| **The hash chain** | logs written in Capsule's format | no earlier decision was edited |

The reader tolerates other systems' formats. It looks for the price, the transaction hash,
the chain, the endpoint and the error code under the names those systems use: `price_usd`,
`amount_usd`, `cost.usd`; `tx_hash`, `tx`, `settlement.tx`; `network`, `settlement.network`;
`service`, `provider`, `target.provider`. A field it cannot find is left empty, never guessed.

There is a worked example, written in a flat schema with no hash chain and different keys:

```
https://capsule-phi-blond.vercel.app/examples/foreign-log.jsonl
```

Its payments are confirmed exactly as ours are. Its hash chain is skipped, and the answer says so.

The fetcher only fetches https, resolves the host once and **connects to the address it
checked**, refuses any non-public address, re-checks every redirect hop, and caps the size
and the time.

## Use it from an agent

No wallet, no account. A URL is the credential.

**MCP** (stdio), one command, straight from this repository:

```bash
npx -y github:unifyWeb3/capsule
```

It runs the TypeScript in this repository, so the code that answers is the code you can
read. The same three tools are packaged for npm as `@oxunify/capsule-mcp`, so
`npx -y @oxunify/capsule-mcp` is the same server from the registry.

Or, from a clone:

```bash
npm run mcp
```

```json
{
  "mcpServers": {
    "capsule-verifier": {
      "command": "node",
      "args": ["--import", "tsx", "/path/to/capsule/mcp/server.ts"]
    }
  }
}
```

Three tools. `verify_record(log_url, budget_usd?)` returns the full published proof for any
log. `get_proof()` returns this deployment's own recorded run, re-read from the chain at call
time. `price_my_limit(facts?, per_tx_usd?, total_usd?, catalog?)` prices what a set of caps
costs for a set of facts, says which cap forbade what, and takes `catalog: "live"` to price
over today's Kite catalog.

**HTTP**, paid by the caller: `POST /api/verify` with `{"log_url": "..."}`. $0.001 USDC per
verification, x402 on Base. Non-2xx answers cancel settlement, so a buyer never pays for a
log that cannot be verified.

**Browser**: `/verify`, paste a log URL and watch the check happen step by step.

## The asymmetry

One thing in this project is still not proven.

> **The payments are chain-verified. The refusals are corroborated by the payment network's
> own ledger, but not attested by the agent.**

A payment leaves a transaction, so anyone can re-read it. A refusal leaves nothing. It
exists in the signed log, in the Passport's error code, and now in a second record this
project did not write: the Passport's activity ledger holds every payment that session
made and no payment for either refusal. That is much closer to proof than the owner's word
was, and it is still not the same as an attestation transaction the agent signs for each
refusal.

Closing the rest of the gap means one attestation transaction per refusal, signed by the
agent. It needs a wallet and a few cents of gas. It has not been done.

## Capability → mechanism → code

| Capability | Mechanism | Code |
| --- | --- | --- |
| The agent decides what to buy | SERV Reasoning, chat completions with a strict JSON schema | `src/serv.ts` |
| The agent buys one fact at a time | A bounded loop: one fact, one proposal, one purchase | `src/agent.ts` |
| Relevance is decided by code, not the model | The catalog says what each endpoint returns; the code shortlists | `src/menu.ts` |
| The limit is never decided by this repository | The code does not filter by budget; the Passport decides | `src/agent.ts`, `src/kpass.ts` |
| The spending limit is the user's | A Kite Passport session, approved with a passkey, enforced in Kite's backend | `kpass session create --separate` |
| The refusal is the product | `session_rule_exceeded` and `session_total_exceeded` are read as state, not as errors | `src/kpass.ts`, `src/agent.ts` |
| The record cannot be quietly edited | An append-only keccak-256 hash chain | `src/log.ts` |
| The record belongs to an identity | The head is signed with the agent's runtime key, checked against Kite's published key set | `src/attest.ts` |
| The proof is re-checked, not remembered | `/proof.json` reads each transaction and its transfer log at request time | `src/proof.ts` |
| What a limit costs is solved, not asserted | Exact enumeration over fact subsets against the catalog, with the recorded run as the regression test | `src/limit-cost.ts` |
| Your facts are priced at today's prices | The Kite service catalog is a public read; the calculator reads it live and says when | `src/catalog-live.ts` |
| The refusals have a second, independent record | The Passport's own ledger is captured, redacted, and reconciled against the log | `src/ledger.ts` |
| The numbers are not typed by hand | Every figure is generated from the receipts; `npm run readme` regenerates the tables above | `scripts/generate-readme.ts` |

## Run it yourself

```bash
git clone https://github.com/unifyWeb3/capsule.git && cd capsule
npm install
cp .env.example .env      # set PAY_TO to an address you control
npm test                   # no network, no keys, no money
npm run verify             # the checks against the live deployment
npm run audit              # every page in a real browser, at two widths
npm start                  # the merchant on :8080
npm run mcp                # the verifier and the limit calculator as MCP tools
```

`npm run audit` loads every page in Chromium at 1440px and 390px and checks for console
errors, failed requests, overflow, contrast below 4.5:1, and whether the page rendered the
elements it is supposed to render. A page that catches its own exception and shows a tidy
red box still reports no console error; the rendered-content check is the one that matters.

## Honest limitations

- The pilot's caps are tiny ($0.002 per call, $0.0025 in total). The scale is set by a small
  test wallet, not by the design.
- Our own service could not be paid. Its host is not on the Passport's allowlist, so the run
  buys from third-party merchants and we earn nothing.
- The refusals are corroborated by the payment network's ledger, not attested by the agent,
  as above. The payments are not.
- The settlement chain is Base, not Kite chain. Settling on Kite chain instead is a
  configuration change, not a redesign, but it is untested here.
- The agent's endpoint choices come from a curated menu, not the whole catalog. The
  calculator prices over the whole catalog.
- A cover in the calculator is either demonstrated (the record shows the endpoint being
  chosen for that fact) or declared (the merchant's own catalog text claims it). A
  declared cover is the merchant's claim, not a purchase, and the answer says which is
  which. A cover the record already paid for keeps that price, which is a price from its
  day, not today's.
- One task, one agent, one session. No multi-agent orchestration, no retry policy, no
  database, no queue.
